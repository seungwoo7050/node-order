상태: 확정(오케스트레이터). 엔진 선택(PG 우선, 교체 가능)만 확정(사람)
브랜치: 26-search (앞 브랜치: 25-harness)
문제: 손님은 상품 목록을 id 순서로 넘겨 보는 것 말고는 상품을 찾을 수 없다. 상품이 수십 개를 넘으면 원하는 상품에 닿지 못하고, 판매자는 손님이 무엇을 찾는지 모른다. LIKE '%검색어%'를 바로 붙이면 순차 스캔이 되어 상품이 늘수록 DB 부하가 커지고, 오타와 띄어쓰기 차이를 견디지 못한다.
결정:
  - 검색은 `SearchEngine` 인터페이스(`search`, `suggest`, `index`, `remove`, `reindexAll`) 뒤에 두고, 첫 구현은 PostgreSQL이다. 같은 계약 테스트(contract test)를 구현마다 돌린다 / 대안: Elasticsearch(nori). 1인 운영과 서버 한 대 조건에서 JVM 메모리 1~2GB, 이중 쓰기, 재색인 운영 면적이 늘어난다 / 바꿀 신호: 상품 1만 개 초과, 검색 p95가 아래 측정 기준의 3배를 넘음, 형태소 분석(어간, 동의어)이 필요해짐. 그때 ES 구현을 같은 계약 테스트로 더한다
  - 색인은 상품 테이블과 분리한 검색 문서 테이블(`product_search`: 상품 id, 이름, 카테고리 경로 이름, 설명, 2-gram 토큰의 tsvector)이다 / 대안: products에 생성 칼럼과 인덱스를 바로 단다. 카테고리 이름이 바뀌면 상품 행을 모두 고쳐야 하고, 엔진을 바꿀 때 경계가 없다 / 바꿀 신호: 검색 문서가 상품 행과 늘 1:1로 같고 지연 반영이 문제가 되면 합친다
  - 한국어는 공백으로 단어를 나누고 각 단어를 2글자씩 잘라(2-gram) `simple` 설정 tsvector로 넣는다. 검색어도 같은 방식으로 잘라 AND로 찾는다. 1글자 단어는 그대로 토큰으로 둔다 / 대안: pg_trgm만 쓴다. 3-gram이라 2글자 단어("가방")에 약하다. 형태소 확장(mecab-ko 등)은 RDS에 설치할 수 없다 / 바꿀 신호: 2-gram 때문에 엉뚱한 상품이 상위에 자주 뜨면(정밀도 문제) 가중치나 엔진을 바꾼다
  - 오타 대응은 상품 이름에 `pg_trgm` GIN 인덱스를 두고 `word_similarity`로 찾는다. 2-gram 결과가 없거나 적을 때만 보충 결과로 섞는다. 순위는 `ts_rank`(2-gram)와 이름 유사도를 정한 가중치로 더한 값이며, 가중치는 상수 한 곳에 둔다 / 대안: 항상 두 조건을 OR로 묶는다. 결과가 흐려지고 느려진다
  - 색인 반영은 outbox 방식이다. 상품·카테고리를 고치는 트랜잭션 안에서 `search_dirty`(상품 id가 기본키라 같은 상품을 여러 번 고치면 한 행으로 합쳐짐)에 기록하고, 리더 인스턴스의 색인 작업이 `FOR UPDATE SKIP LOCKED`로 가져가 반영한 뒤 지운다. 실패하면 행을 남겨 다음 회차에 다시 한다 / 대안: 기존 `outbox_events`를 넓힌다. 그 테이블은 사용자 알림·메일용이라(`user_id` 필수, 메일을 큐에 넣음) 성격이 다르다. 대안: 쓰기 경로에서 바로 색인. 색인이 실패하면 상품 수정까지 실패한다 / 바꿀 신호: 색인 말고도 상품 변경을 받아야 할 소비자가 생기면 일반 이벤트 테이블로 바꾼다
  - 색인 작업은 별도 프로세스가 아니라 API 프로세스 안의 리더 작업(기존 `leader/` 패턴)으로 돌린다. 재색인은 `npm run search:reindex` 명령이다 / 대안: `search-indexer` 컨테이너 분리. 서버 한 대에서 배포 단위와 관리 대상만 는다 / 바꿀 신호: 색인 작업 때문에 API p95가 눈에 띄게 오를 때
  - API: `GET /products/search?q=&page=`(페이지 크기 20, 최대 5쪽. 순위 정렬이라 id 커서를 쓸 수 없다), `GET /products/suggest?q=`(상품 이름 최대 8개), `GET /search/popular`(최근 7일 상위 10개). 검색 결과는 카탈로그 캐시에 넣지 않는다(키가 끝없이 는다). 재고와 이미지 URL은 목록과 같은 방식으로 붙인다
  - 인기 검색어는 Redis 일별 ZSET(`search:popular:YYYYMMDD`, TTL 8일)에 정규화한 검색어(소문자, 공백 정리)를 더하고, 7일치를 합쳐 상위를 낸다. 같은 IP·같은 검색어는 1시간에 한 번만 센다(`SET NX EX`). 결과가 0건인 검색어는 따로 센다(`search:zero:...`). 판매자가 손님이 못 찾은 것을 보게 된다(화면은 29에서 만든다) / 대안: DB 테이블. 쓰기가 잦고 정확도는 중요하지 않다
  - 화면: 상점 머리글에 검색 상자(콤보박스 접근성: 화살표 키, Enter, Esc, `aria-activedescendant`), 입력 200ms 디바운스 자동완성, `/shop/search?q=` 결과 페이지(결과 없음 안내와 인기 검색어 칩), 주소의 q가 원본이다
  - 측정: 벤치용 시드 명령(상품 1만 개, 테스트 DB에만)으로 LIKE와 새 쿼리의 `EXPLAIN (ANALYZE, BUFFERS)`와 p50·p95를 재서 README의 측정 절에 적는다. 이 PC에서 잰 값이며 실제 트래픽이 아니라고 밝힌다
  - 25의 하네스 빈틈 하나를 같이 막는다: verify의 포트 점유 검사에 가드 테스트(막을 예와 통과할 예)를 더한다
완료 기준:
  1. 2-gram 검색: 상품 "여행용 가방"이 검색어 "가방"과 "여행가방"으로 나온다. "가"처럼 1글자 검색어는 400이 아니라 빈 결과나 이름 접두 일치로 답한다
  2. 오타 검색: "블루투스 이어폰"이 "블루투스 이어펀"과 "블르투스 이어폰"으로 나오고, 정확히 맞춘 상품이 오타 보충 결과보다 위에 있다
  3. 반영: 상품 이름을 바꾸고 색인 작업을 한 번 돌리면 새 이름으로 나오고 옛 이름으로는 안 나온다. 카테고리 이름을 바꾸면 그 카테고리 상품이 새 카테고리 이름으로 나온다. 같은 상품을 연달아 3번 고치면 `search_dirty`는 1행이다
  4. 장애 격리: 색인 작업이 예외를 던져도 `GET /products/search`와 상품 수정 API는 200이고, dirty 행이 남아 다음 회차에 반영된다
  5. 재색인: `npm run search:reindex`를 두 번 돌려도 `product_search` 행 수가 상품 수와 같고 결과가 같다
  6. 인기 검색어: 같은 IP가 같은 검색어를 10번 검색해도 1로 세고, 다른 IP 3곳이면 3이다. 0건 검색어는 따로 쌓인다
  7. 계약 테스트: `SearchEngine` 계약 테스트 묶음이 PG 구현에 대해 통과한다(다른 구현이 재사용할 수 있게 구현을 주입받는 모양)
  8. 웹 e2e: 검색 상자에 입력하면 자동완성이 뜨고, 화살표와 Enter로 상품을 고르며, Enter만 누르면 결과 페이지로 가고, 결과가 없으면 인기 검색어 칩이 보인다
  9. 측정: 벤치 데이터에서 새 검색 쿼리의 실행 계획에 GIN 인덱스 스캔이 나오고(순차 스캔 아님), LIKE와 비교한 수치가 README에 있다
  10. `npm run verify` 통과. 테스트 수가 25 끝보다 늘고 줄지 않는다. 포트 검사 가드 테스트가 있다
범위 밖: Elasticsearch 구현, 형태소 분석·동의어, 개인화·추천, 검색 분석 관리자 화면(29), 검색 결과 캐시, 필터·정렬 옵션(가격순 등)
외부 의존: 없음 (pg_trgm은 RDS에서 쓸 수 있는 확장)
