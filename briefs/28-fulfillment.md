상태: 확정(오케스트레이터)
브랜치: 28-fulfillment (앞 브랜치: 27-toss-payments)
문제: 주문은 "미결제·결제 완료·취소" 세 가지(`paid`, `canceled_at`)뿐이다. 판매자는 결제 뒤 배송을 준비하고 송장을 붙이고 반품을 받아 줄 방법이 없고, 손님은 내 주문이 어디쯤인지와 언제까지 청약철회를 할 수 있는지 모른다. 배송지도 받지 않아서 실물을 보낼 수 없다. 27에서 환불(돈)은 생겼지만, 그 환불을 언제 누가 몇 번 부르는지 정하는 곳이 없다.
결정:
  - 주문 상태를 하나의 칸(`orders.status`)과 순수 함수 상태 기계로 둔다. 상태는 pending_payment → paid → preparing → shipped → delivered → confirmed와 canceled, 반품은 주문이 아니라 `returns` 요청 단위다. 전이 표(현재 상태 × 사건 → 다음 상태, 허용하는 행위자)를 코드 한 곳에 두고, DB 반영은 조건부 update(`WHERE id = ? AND status = <from>`)로 해서 동시 요청 중 하나만 이긴다. 모든 전이는 `order_status_history`(from, to, 행위자, 사유, 시각)에 남긴다 / 대안: 상태 기계 라이브러리(XState 등). 전이가 열 개 남짓이라 표 하나로 충분하고, 동시성은 라이브러리가 아니라 DB가 지킨다 / 바꿀 신호: 상태가 병렬 영역(결제·배송·반품이 서로 독립적으로 움직임)을 가져야 하면 라이브러리를 고려한다
  - 기존 `paid`·`canceled_at`은 지우지 않고(expand), 새 마이그레이션이 status를 백필하고 앱이 둘을 같이 맞춘다. contract는 다음 단계 신호로 남긴다(24의 순서)
  - 배송지: 주문에 수령인, 연락처, 우편번호(5자리), 주소, 상세주소, 배송 메모를 담는다. 결제 시작 전에 필수 검증을 한다. 연락처와 주소는 로그에 마스킹한다 / 대안: 주소록 테이블. 1인 상점의 첫 판매에는 주문에 붙은 사본이면 되고, 나중에 주소를 바꿔도 지난 주문의 배송지는 바뀌면 안 된다
  - 배송비 정책: 기본 3,000원, 상품 합계 50,000원 이상이면 무료. 상수 한 곳에 두고(설정 화면은 29) 주문에 `shipping_fee`를 따로 저장하며, `total_amount`는 배송비를 포함한다. PG 승인 금액 대조(27)는 이 total과 비교한다 / 바꿀 신호: 도서산간 추가 요금이나 상품별 배송비가 필요해지면 정책 객체로 바꾼다
  - 송장: `shipments`(주문, 택배사 코드, 송장번호, 발송 시각). 택배사는 고정 목록(CJ대한통운, 우체국, 한진, 롯데, 로젠)과 조회 링크 템플릿이다. 배송 추적 API는 쓰지 않는다 / 대안: 추적 API(유료 키). 바꿀 신호: 송장 상태를 손으로 바꾸는 일이 하루 수십 건을 넘을 때
  - 자동 전이: shipped 뒤 5일이 지나면 delivered, delivered 뒤 7일이 지나면 confirmed. 리더 작업(기존 `leader/` 패턴)이 하고, 조건부 update라 여러 번 돌아도 같다. 관리자는 배송완료를 손으로 앞당길 수 있고, 손님은 구매확정을 누를 수 있다
  - 취소: 관리자가 paid·preparing 주문을 취소하면 한 트랜잭션에서 상태 전이와 재고 복구를 하고, 커밋 뒤 27의 `RefundsService.request`를 멱등 키 `cancel-<주문id>`로 전액 부른다. 다시 눌러도 조건부 update가 지고 멱등 키가 같아서 재고와 환불이 한 번만 일어난다 / 대안: 환불 성공 뒤에 상태를 바꾼다. PG가 느리면 그동안 배송 준비가 진행될 수 있다
  - 반품·교환: 손님은 delivered 뒤 7일 안(청약철회 기간, 구매확정 전)에 상품별 수량과 사유(단순변심·상품 하자·오배송)로 요청한다. `returns`(주문, 종류 refund·exchange, 상태 requested·approved·rejected·completed, 사유, 항목). 관리자가 승인하면 한 트랜잭션에서 요청 상태 전이(조건부)와 반품 수량 재고 복구를 하고, 커밋 뒤 환불을 멱등 키 `return-<반품id>`로 부른다. 환불액은 항목 금액 합계이고, 단순변심이면 왕복 배송비(6,000원)를 뺀다. 하자·오배송이면 빼지 않는다. 교환은 환불하지 않고 반품 수량을 복구하고 교환품 수량을 차감한 뒤(재고가 없으면 409) 새 송장을 받는다 / 바꿀 신호: 교환 차액 결제가 필요해지면 교환을 새 주문으로 바꾼다
  - 알림: 상태가 바뀔 때마다 같은 트랜잭션에서 outbox 이벤트(`order.preparing`, `order.shipped`, `order.delivered`, `order.canceled`, `return.approved`, `return.rejected`)를 남기고, 기존 relay가 종류별 메일 템플릿으로 메일 큐에 넣는다. 이벤트 하나에 메일 하나다
  - 화면: 손님의 내 주문 상세에 상태 타임라인, 송장 조회 링크, 반품 신청(기간이 남았을 때만), 구매확정 버튼을 둔다. 관리자 주문 목록(상태 필터)과 주문 상세에서 할 수 있는 동작(배송 준비, 송장 입력, 배송 완료, 취소, 반품 승인·거절)은 지금 상태에서 허용된 것만 보인다. 대시보드 집계는 29에서 한다
  - demo_admin은 화면은 보지만 상태를 바꾸는 동작은 막는다(기존 데모 규칙)
완료 기준:
  1. 상태 기계 단위 테스트가 모든 (상태, 사건) 쌍을 표로 돌린다. 허용된 전이만 통과하고 나머지는 모두 거부된다
  2. API: 허용되지 않은 전이는 409와 현재 상태를 돌려준다. 같은 주문에 "송장 입력"을 동시에 두 번 보내면 하나만 성공하고 history는 한 행이다
  3. 취소: 결제 완료 주문을 취소하면 PG 시뮬레이터의 환불 호출이 1회, 재고 복구가 1회다. 같은 요청을 연달아 또는 동시에 보내도 같다
  4. 반품: delivered 뒤 7일 안에는 신청되고, 7일이 지났거나 구매확정 뒤면 409다. 승인하면 환불액이 규칙대로다(단순변심이면 배송비 차감, 하자면 전액). 승인을 두 번 눌러도 환불과 재고 복구는 1회다. 환불이 시간 초과면 반품은 approved로 남고, 27의 환불 확정 명령이 마무리한다
  5. 교환: 승인하면 환불 호출 0회, 반품 수량 복구, 교환품 수량 차감이 일어나고 새 송장을 넣을 수 있다. 재고가 모자라면 409이고 아무것도 바뀌지 않는다
  6. 배송비: 합계 49,000원이면 52,000원, 50,000원이면 50,000원이 PG 승인 금액과 같다(토스·Stripe 시뮬레이터 둘 다)
  7. 배송지: 필수 칸이 비었거나 우편번호가 5자리가 아니면 결제를 시작하지 않고 400이다. 로그에 연락처 원문이 남지 않는다
  8. 택배사별 조회 링크가 템플릿대로 만들어지고, 목록에 없는 택배사 코드는 400이다
  9. 자동 전이 작업을 같은 시각으로 두 번 돌려도 결과가 같고, 기준일 전 주문은 바뀌지 않는다(시계를 주입해 테스트)
  10. 상태가 바뀔 때마다 fake mailer가 해당 템플릿 메일을 정확히 1통 받는다
  11. 웹 e2e: 손님이 주소를 넣고 결제(시뮬레이터) → 관리자가 배송 준비·송장 입력·배송 완료 → 손님이 송장 링크를 보고 반품 신청 → 관리자 승인 → 손님 화면에 환불 금액과 상태가 보인다
  12. `npm run verify` 통과. 테스트 수가 27 끝보다 늘고 줄지 않는다
범위 밖: 배송 추적 API, 도서산간 추가 배송비, 부분 발송, 비회원 주문, 교환 차액 결제, 반품 수거 예약, 설정 화면(29), 옛 칸 contract
