상태: 확정(오케스트레이터)
브랜치: 29-admin (앞 브랜치: 28-fulfillment)
문제: 판매자는 아침에 "오늘 처리할 것"을 한눈에 볼 곳이 없다. 주문 목록·반품·재고를 따로 열어야 하고, 손님이 무엇을 찾다 못 찾았는지(26의 0건 검색어)는 화면에 없다. 우리 DB의 결제·환불과 PG가 아는 결제가 어긋나도(웹훅 누락, 시간 초과 환불, PG 쪽 수동 취소) 아무도 모른다. 사업자 정보·약관·개인정보처리방침·배송비는 코드나 상수에 있어서 판매자가 바꾸려면 배포해야 하고, 전자상거래법 표시 의무를 채울 화면이 없다.
결정:
  - 대시보드 API `GET /admin/dashboard` 하나가 타일 값을 돌려준다: 오늘(Asia/Seoul 자정 기준) 주문 수와 순매출(결제액 − 성공한 환불액), 처리 대기(paid 미착수, preparing, 반품 requested), 재고 부족(설정의 기준 이하), 0건 검색어 상위 10, 미해결 대사 불일치 수. 타일마다 해당 목록으로 가는 링크를 둔다. 캐시하지 않는다(관리자 한 명, 작은 쿼리) / 대안: 집계 테이블·물질화 뷰. 주문 수천 건 규모에서는 이득보다 갱신 경로가 늘어난다 / 바꿀 신호: 대시보드 쿼리가 200ms를 넘을 때
  - 하루 경계는 DB 쿼리에서 `AT TIME ZONE 'Asia/Seoul'`로 명시한다. 서버 시간대에 기대지 않는다
  - PG 대사: `PaymentGateway`에 `listTransactions(기간)`을 더한다(토스 거래 조회, Stripe 결제 목록·환불 목록. 시뮬레이터도 같이). 대사는 기간 안의 PG 거래와 우리 payments·refunds를 양쪽에서 맞춰 본다. 불일치 종류는 amount_mismatch, status_mismatch(우리는 paid, PG는 취소 등), missing_in_db(PG에만 있음), missing_in_pg(우리에만 있음), refund_mismatch(성공 환불 합계와 PG 취소 금액이 다름)다. 먼저 27의 결과 미상 환불 확정을 돌린 뒤 대사한다 / 대안: payments를 하나씩 `fetchPayment`로 재조회. PG에만 있는 결제를 못 찾는다
  - 대사 결과는 `reconciliation_runs`(기간, provider, 시작·끝, 건수, 실패 사유)와 `reconciliation_issues`(provider, 기준일, 종류, PG 결제 키의 자연 키 unique, 우리 값, PG 값, 처음·마지막 발견 시각, 해결 시각·메모)에 둔다. 다시 돌리면 같은 키를 upsert하므로 불일치 집합이 같다. 해결 표시한 건은 값이 그대로면 해결 상태를 유지하고, 값이 바뀌면 다시 연다 / 대안: 실행마다 새 행. 다시 돌릴 때마다 건수가 불어나 "결과가 같다"를 확인할 수 없다
  - 대사는 매일 04:00(Asia/Seoul)에 전날 분을 리더 작업으로 돌리고, `npm run payments:reconcile -- --date=YYYY-MM-DD`로 손으로도 돌린다. provider 하나가 실패해도 나머지는 진행하고, 실패를 run에 기록하며, 명령은 0이 아닌 종료 코드를 낸다
  - 상점 설정은 한 행짜리 타입 있는 테이블 `store_settings`(상호, 대표자, 사업자등록번호, 통신판매업 신고번호, 주소, 연락처, 이메일, 개인정보 보호책임자, 배송비 기본·무료 기준·반품 왕복 배송비, 재고 부족 기준)와 `version` 칸이다. 저장할 때 `If-Match: <version>`이 다르면 409를 낸다(낙관적 잠금). 28의 배송비 상수는 이 설정을 읽게 바꾸고, 주문은 생성 시점의 배송비를 저장하므로 지난 주문은 바뀌지 않는다 / 대안: key-value 테이블. 칸별 검증과 타입이 흐려진다
  - 약관·개인정보처리방침·청약철회 안내는 `legal_documents`(종류, 버전, 본문, 시행일) 버전 행으로 둔다. 바꾸면 새 버전이 생기고 지난 버전은 공개 페이지에서 볼 수 있다(개인정보처리방침 변경 이력 공개). 결제할 때 손님이 개인정보 수집·이용(배송지)에 동의해야 하고, 주문에 동의한 문서 버전과 시각을 남긴다
  - 사업자등록번호는 10자리 체크섬으로 검증한다
  - 비밀값(PG 키, 오류 추적 DSN, LLM 키)은 환경변수에만 두고 설정 화면에서 받지 않는다. 화면은 `/features`로 "연결됨·없음"만 보인다. 설정 API의 스키마에는 비밀 칸이 없다 / 대안: 암호화해 DB에 저장하고 쓰기 전용 칸으로 받는다. 키 관리(KMS)와 회전 경로가 생겨 1인 운영 면적이 늘어난다 / 바꿀 신호: 개발자가 아닌 판매자가 직접 키를 넣어야 할 때
  - 법적 표시: 상점의 모든 페이지 바닥글에 사업자 정보를 표시하고 `/legal/terms`, `/legal/privacy`, `/legal/refund` 페이지를 둔다. 콘솔은 설정을 태그 캐시로 받고, 설정을 저장하면 그 태그를 다시 검증해 배포 없이 바뀐다. API도 설정을 메모리에 캐시하고 저장할 때 무효화한다(인스턴스가 둘이면 Redis pub/sub로 무효화)
  - 화면: `/admin`(대시보드 타일), `/admin/reconciliation`(불일치 목록, 종류 필터, 해결 표시·메모), `/admin/settings`(폼, 칸별 오류, 저장 충돌 안내, 연결된 기능 표시), `/admin/legal`(문서 편집·버전 목록). demo_admin은 모두 보지만 쓰기는 403이다
완료 기준:
  1. 대시보드: 자정(Asia/Seoul) 앞뒤로 만든 주문과 부분 환불이 섞인 데이터에서 오늘 주문 수와 순매출, 처리 대기 수, 재고 부족, 0건 검색어가 기대값과 같다
  2. 대사: 시뮬레이터에 불일치 다섯 종류를 하나씩 심으면 각각 맞는 종류로 기록되고, 일치하는 결제는 기록되지 않는다. 두 번 돌려도 불일치 키 집합과 건수가 같다. 해결한 건은 값이 그대로면 해결 상태를 유지한다
  3. 대사 부분 실패: provider 하나의 거래 조회가 500이어도 다른 provider는 대사되고, run에 실패가 남고, 명령의 종료 코드가 0이 아니다
  4. 설정: 저장하면 상점 바닥글과 `/legal/*`가 배포 없이 새 값을 보인다(웹 e2e). 오래된 version으로 저장하면 409이고 화면에 충돌 안내가 보인다
  5. 사업자등록번호 체크섬이 틀리면 400이다(맞는 예와 틀린 예를 테스트)
  6. 배송비 설정을 바꾸면 새 주문에만 적용되고, 지난 주문의 total_amount와 PG 승인 금액 대조는 그대로다
  7. 개인정보처리방침을 고치면 새 버전이 생기고 지난 버전을 열람할 수 있다. 결제할 때 동의하지 않으면 400이고, 주문에 동의 버전이 남는다
  8. 비밀값 분리: 설정 API와 관리자 페이지 응답 어디에도 환경변수 비밀값(PG 키 등)이 없다(응답 전체를 검사하는 테스트). 기능 표시는 연결됨·없음뿐이다
  9. demo_admin은 대시보드·대사·설정을 읽을 수 있고, 모든 쓰기가 403이다
  10. `npm run verify` 통과. 테스트 수가 28 끝보다 늘고 줄지 않는다
